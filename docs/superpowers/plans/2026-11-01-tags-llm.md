# Tag Suggestions on LlmClient and Reviewed LLM Consolidation — Implementation Plan

**Spec:** `docs/superpowers/specs/2026-10-31-tag-management-design.md`, sections "3. Reviewed LLM
consolidation", "5. Save-time suggestions", "6. Shared LLM port", "Guards for the Haiku default",
and Rollout steps 3–4.
**Branch:** `feat-tags-llm`
**Goal:** save-time suggestions and tag consolidation both run on the shared `LlmClient` port, with
Claude Haiku 5.5 as the default text model. Consolidation is a background job that only writes
proposals; a review screen at `/tags/review` applies the rows the user checks as one undoable
batch. **Nothing changes a user's tags without the user's click.**

## Auto-pilot decisions

The superpowers and auto-pilot skills are not installed on this host, so I ran the planning
questions myself and answered each from the spec, the lab harness, the code, or the task brief. No
human gate.

| Question | Answer | Evidence |
|----------|--------|----------|
| Which pairs are pre-checked? | Groups built only from pair-check `high` verdicts or whole-list `high` proposals. `medium` pair verdicts form separate rows under "Check these", listed first, unchecked, with "Select all". `low` "same" verdicts are not proposed. | Spec guard recommendation 3 and 5; `guards.py` rule "whole-list high OR pair check high"; whole-list `low` precision was 0.23–0.25 |
| What is cannot-link? | Every pair the pair check answered "not same" (echo matched). A union that would put two such tags in one group is skipped, in both tiers. A whole-list `high` pair the pair check rejected is therefore blocked. | `guards.py` line 102 (`cannot = answered and not same`), `hosted_eval.fold_pairs` |
| Echo mismatch? | The verdict is dropped: no edge and no cannot-link. | Spec: "mismatched answers are dropped"; an answer meant for another pair says nothing about this one |
| Empty whole-list answer? | Retry once when no valid group comes back; then continue with string candidates only. | Spec "The empty whole-list answer"; `hosted_eval.step_consolidate(retries=1)` |
| Symbol handling in candidates? | The candidate key spells symbols out (`#` → `sharp`, `+` → `plus`) instead of dropping them, so `c#` is not `c` and `c#` never matches `continuous integration`, while `c++`/`cpp` and `c#`/`csharp` still become candidates. | Spec guard 1 ("`c#` is not `c`"); the `c#`~`continuous integration` wrong pair |
| What does the LLM see? | The L1–L3 normalization groups (one unit per group: display form, summed count, one sample title), most used first, capped at 1,000 units; pairs capped at 800 (20 calls of 40). | Spec §3 "Input"; bounded cost and latency for very large libraries |
| How do LLM proposals relate to the deterministic ones? | The job first refreshes the deterministic proposals. An LLM proposal's members are unit display forms. Applying an LLM row also applies the pending deterministic rows of its units in the same batch (the row shows their spellings), so `GitHub`/`github`/`gh` merge in one step and chains resolve through `merge_mapping`. | `merge_mapping` follows chains; listing every raw spelling in both rows would make two different targets for one spelling and fail the apply |
| Canonical of an LLM group? | The whole-list call's canonical when it is in the group; otherwise the display rule (`choose_display`) over the units. Editable on the review screen before apply. | Spec §3 review screen ("the canonical tag (editable)") |
| Job state: memory or table? | Table `tag_consolidation_jobs` (migration `017_tag_consolidation.sql`), one row per user with a `run_id`. A `running` row older than 60 minutes (longer than the slowest run: 42 calls at the 60 s timeout) counts as failed, and only the current run may store proposals or record its outcome. | Survives restarts and works with more than one machine; the brief allows a migration for job state (017; search embeddings takes 018) |
| Where does the old in-memory job set go? | Removed from `AppState` with the one-click button. | Replaced by the job table |
| Suggestions: where do canonical tags come from? | `EnrichmentService` loads them itself through a new read-only `TagVocabulary` port (implemented by `TagAliasService`): canonical units most used first, top 300, plus up to 200 more whose words appear in the URL, title or description. Handlers stop passing raw `tags_with_counts`. | Spec §5 step 1; the web add-suggest handler passed `None` today, so it sent no tags at all |
| Resolve suggestions before showing them? | Yes, read-only: `TagVocabulary::preview_tags` runs the pure resolver on the alias rows and tag counts without writing aliases. The save path resolves again (and writes). | Spec §5 step 4; showing must not write alias rows for a suggestion the user may discard |
| Enum casing? | Matched exactly. The adapter already rejects answers outside the exact enum, so a case-insensitive mapping would be dead code (PR 46 review). | `adapters::llm_client::matches_schema` checks `enum` before the use case sees the answer |
| Default model? | `DEFAULT_ANTHROPIC_MODEL = "claude-haiku-5-5"`, Haiku 5.5 added first in the options, Haiku 4.5 kept for saved settings. No migration: every write sets the model explicitly. Effort stays `low` through `ANTHROPIC_EFFORT`. | Spec "Model choice"; `llm_settings_repo` upsert binds the model |
| Image prompt assistant? | Moved onto `LlmClient` too (`LlmClientPromptAssistant`, schema `{"prompt": string}` and the existing `validate_assisted_image_prompt`). | Needed to delete `anthropic.rs`, the text half of `openai.rs` and `llm_router.rs` ("the duplicated vendor code that LlmClient replaces") |
| Feature port signatures? | `LlmEnricher::enrich` and `LlmPromptAssistant::assist_image_prompt` take the provider explicitly; the model-prefix guessing defaults go. | Provider comes from settings; guessing was only for routers that no longer exist |
| PR 41 finding (a)? | `merge_mapping` rejects a batch in which two spellings with the same compact key end up at different targets, and a target whose key another spelling leaves for a different target. | One alias key can point at one canonical only; the repo silently kept the last one |
| PR 41 finding (b)? | `replace_pending_proposals` takes the per-user advisory lock first. | Two concurrent runs could each delete and then both insert |
| Fake LLM for E2E? | A small Node llama.cpp-compatible server (`scripts/e2e/fake-llm.mjs`) started by Playwright; `start-server.sh` pins `LLM_BACKEND=llamacpp` to it. It answers by schema shape. No vendor call can leave the E2E server. | The `LlamaCppLlmClient` adapter already exists; no test-only code in the server |
| E2E without Docker? | `start-server.sh` honours `E2E_DATABASE_URL` (skips devproxy, resets the E2E user with `psql`). | This host has no Docker; CI does not run Playwright |
| What exactly does Apply merge? | Exactly the rows the page showed. Each checked row posts its spellings; one transaction under the per-user lock resolves the pending proposals through the current aliases, refuses if any checked row is gone, not pending, or would merge other spellings, saves edited targets and applies the batch (PR 46 review). | Hard rule: nothing the user did not see is merged |
| A run where every call failed? | An error: the job fails with a safe message and the pending AI proposals stay (PR 46 review). | An outage must not read as "no duplicates" and delete unreviewed suggestions |
| CI | One step in "Postgres idempotency" for the new ignored test module. | Brief |

## Steps

Each step ends with `cargo test -p boopmark-server` green and a commit.

1. **PR 41 fixes.** `merge_mapping` same-key conflicts (domain test); advisory lock in
   `replace_pending_proposals`.
2. **Haiku 5.5 default.** `llm_settings.rs` constants and tests, settings page tests and
   `tests/e2e/settings.spec.js` option list.
3. **Suggestions on `LlmClient`.** `app/tag_llm.rs`: `LlmClientEnricher` (enum schema, one `new`,
   case-insensitive enum match, bounds), `TagVocabulary` port + `TagAliasService` impl
   (`canonical_tags`, `preview_tags`), `EnrichmentService` uses it; handlers simplified.
   `LlmClientPromptAssistant` in `app/image_prompt.rs`. Delete `anthropic.rs`, `openai.rs` (text),
   `llm_router.rs`; rewire `main.rs`.
4. **Consolidation domain.** `domain/tag_consolidation.rs`: units from normalization groups,
   symbol-aware `candidate_reason`, whole-list validation, pair list, union-find with cannot-link in
   two tiers, proposals. Unit tests.
5. **Consolidation LLM calls.** In `app/tag_llm.rs`: whole-list request/parse with one retry on an
   empty answer, echo pair check in batches of 40. Stub-`LlmClient` tests.
6. **Job.** Migration 017, `TagConsolidationJobRepository` port + Postgres adapter,
   `TagSample` query on `TagAliasRepository`, `TagConsolidationService` (`start`, `run`, `status`,
   review rows, apply with canonical overrides and deterministic expansion, undo). Remove
   `TagConsolidator`, its adapters, `update_tags_bulk`, `list_id_tags`, the old `tag_samples`,
   `repoint_aliases`.
7. **Review screen.** `templates/tags/review*.html`, routes `/tags/review` (GET),
   `/tags/review/run` (POST AI job), `/tags/review/normalize` (POST), `/tags/review/status`
   (GET, polled), `/tags/review/apply` (POST), `/tags/review/dismiss` (POST),
   `/tags/review/undo/{batch}` (POST). Settings: the Tag Library section links to `/tags` and
   `/tags/review`; the one-click button and its fragment go.
8. **Tests.** Ignored Postgres test: stub LLM → job → proposals → apply → undo. E2E
   `tests/e2e/tag-review.spec.js` with the fake LLM. CI step.
