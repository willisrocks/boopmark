# Generated Bookmark Images Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add opt-in, asynchronous Gemini-generated bookmark images after metadata and screenshot acquisition fail, with manual regeneration, a hard 10-call bulk cap, safe persistence, and production verification.

**Architecture:** Keep Google-specific HTTP details behind a provider-neutral `ImageGenerator` port. Extend the existing bookmark acquisition service with a generated-image coordinator that receives per-user encrypted settings, transient metadata context, object storage, and repository ports; automatic generation is spawned only after the bookmark commit, while manual generation writes the existing override slot. Reuse one application-layer image normalizer for uploads and provider bytes.

**Tech Stack:** Rust 2024, Axum 0.8, Tokio, SQLx/Postgres, reqwest, scraper, image, AES-256-GCM `SecretBox`, Askama/HTMX, SSE, Playwright, Railway, Cloudflare/R2, iOS Simulator.

**Spec:** `docs/superpowers/specs/2026-08-24-generated-bookmark-images-design.md`

## Global Constraints

- Execution mode is supervised Firstmate subagent-driven development: one fresh implementation worker per task, followed by spec-compliance review and code-quality review before the next task.
- Google Gemini is the only production provider in v1, behind the provider-neutral `ImageGenerator` port.
- The model allow-list is exactly `gemini-3.1-flash-lite-image` (default) and `gemini-3.1-flash-image` (quality).
- Gemini keys are per-user, AES-256-GCM encrypted through the existing `SecretBox`, write-only in the UI, and never logged or returned.
- Automatic generation begins only after metadata image and screenshot acquisition both fail and only after the bookmark row is committed and returned.
- Prompt context uses a bounded transient `article`/`main`/`body` excerpt with metadata-description fallback; excerpts and prompts are never persisted.
- Automatic output writes `image_url` with `image_source = 'generated'`; manual **Generate image** writes `override_image_url`; uploaded overrides retain precedence.
- Cards remain unchanged and contain no AI label, pending UI, polling, or shimmer.
- The bulk cap is a hard, non-configurable 10 Gemini calls per run; failed calls consume cap slots.
- There are no automatic retries, backoff, startup recovery, recurring jobs, or durable queues.
- Provider failures use fixed safe messages; raw response bodies, prompts, excerpts, keys, and image bytes never enter HTTP responses or logs.
- All generated bytes are untrusted and must pass bounded decode, dimension/pixel validation, crop/resize, and JPEG re-encode to exactly 1200×630.
- Unit, integration, and browser tests use fakes/local stubs. The real key at `/tmp/gemini.txt` is used only by the isolated ignored live-provider check; never print, log, copy, fixture, track, or screenshot it.
- Pre-existing HTML status handling, remote-image SSRF, unbounded download, and SVG/content-validation defects remain a separate follow-up; do not fold those fixes into these tasks.
