# Generated Bookmark Images — Architectural Design

**Date:** 2026-08-24
**Status:** Draft — awaiting captain review

## Summary

Boopmark will generate a bookmark card image only after metadata-image acquisition and the screenshot fallback both fail. Generation is automatic, asynchronous, per-user opt-in, and Google Gemini-only in v1. The application will nevertheless depend on a provider-neutral `ImageGenerator` port so another adapter can be added without changing domain or application logic.

Each user supplies a Gemini API key, encrypted at rest with Boopmark's existing `SecretBox`, and selects one of two allow-listed models:

- `gemini-3.1-flash-lite-image` — default
- `gemini-3.1-flash-image` — higher-quality option

Automatic output is normalized and stored in Boopmark object storage, then written to `bookmarks.image_url` with internal `image_source = 'generated'`. A manual **Generate image** action in the existing edit modal generates again and writes `override_image_url`, preserving the existing rule that an uploaded or generated override wins over the automatic image. Cards remain quiet: there is no AI label, pending treatment, polling UI, shimmer, or other card change.

## Goals

- Fill genuinely image-less bookmarks without delaying bookmark creation on a model call.
- Preserve the existing acquisition order: metadata image, screenshot, then generated image.
- Keep credentials and model choice per user and independent from Anthropic settings.
- Bound user-triggered bulk generation to exactly 10 provider calls per run.
- Preserve upload precedence and the existing restore-original behavior.
- Prevent provider bytes, errors, credentials, and page content from crossing unsafe boundaries.
- Make normal automated tests deterministic and free of live-provider calls.

## Non-goals

- Providers other than Google in v1.
- AI labels, badges, filters, or provenance text in the UI.
- Persisting article excerpts or prompts.
- Automatic retries, backoff, recurring jobs, a durable queue, or a dead-letter queue.
- Usage billing, quotas, or a spend dashboard beyond the bulk-run cap.
- A separate Generated Images settings form or route.
- Fixing the pre-existing scraper and remote-image-fetch defects listed at the end of this document.
- An implementation plan or implementation sequencing.

## Existing Contracts to Preserve

Boopmark already uses hexagonal ports and adapters, stores system-acquired images in `image_url`, and stores user-chosen images in `override_image_url`. `Bookmark::effective_image_url()` resolves the override first. Generated images follow those contracts rather than introducing a third displayed URL.

All displayed card images converge on 1200×630 JPEG. The generated-image path will reuse the upload override pipeline's header-first dimension checks, decode limits, crop, resize, and JPEG re-encode. Provider output is untrusted even when it comes from Google.

## Architecture

### Provider-neutral port

Add a domain port shaped like the existing dynamically dispatched LLM ports:

```rust
pub trait ImageGenerator: Send + Sync {
    fn generate(
        &self,
        api_key: &str,
        model: &str,
        input: ImageGenerationInput,
    ) -> Pin<Box<dyn Future<Output = Result<Vec<u8>, ImageGenerationError>> + Send + '_>>;
}
```

`ImageGenerationInput` contains only the prompt inputs required for one bookmark: URL/domain, title, description, tags, and an optional bounded transient excerpt. It contains no persistence concerns and no provider-specific request fields. The port returns bytes, never a provider URL; this prevents provider download details or an unsafe URL-fetch path from leaking into the application layer.

`GeminiImageGenerator` is the only v1 adapter. It owns a timeout-configured HTTP client but not a credential or selected model; those are passed per call. It converts Gemini's inline image response to bytes and maps all upstream responses to the fixed internal error taxonomy described below. Provider request/response bodies are never included in `DomainError`, HTTP responses, or logs.

A fake `ImageGenerator` is injected in normal tests. Production composition injects the Gemini adapter. No real-provider behavior is selected by the normal test or E2E configuration.

### Application services

A generated-image application service coordinates:

1. loading the user's generated-image settings and decrypting the key just in time;
2. building a prompt from trusted structure around untrusted bookmark/page text;
3. invoking `ImageGenerator` once;
4. acquiring the image-processing semaphore only after the network call returns;
5. normalizing the returned bytes to a 1200×630 JPEG; and
6. storing either an automatic base image or a manual override through the existing bookmark/storage contracts.

Image normalization moves to an application-level reusable component so uploads and generated bytes use one implementation. Provider-specific code cannot write directly to object storage or bookmark columns.

### Prompt and transient excerpt

The HTML metadata extractor derives a bounded plain-text excerpt while the fetched document is already in memory. Selection order is:

1. visible text under `<article>`;
2. visible text under `<main>`;
3. visible text under `<body>`;
4. metadata description when no usable body excerpt exists.

Extraction collapses whitespace, removes script/style/noscript content, and truncates to one documented character limit before it crosses the metadata port. The exact limit is a code constant covered by tests; it is a memory, privacy, and request-size bound, not a database field. The excerpt is carried in the in-memory acquisition/generation context and captured by the asynchronous task, then dropped. It is never written to `bookmarks`, settings, events, fixtures, or logs.

The prompt clearly delimits title, description, tags, and excerpt as untrusted source material and instructs Gemini to ignore instructions found within them. It asks for a neutral editorial card illustration without logos, UI text, or claims not supported by the supplied context. Prompt construction is a pure function.

## Data and Settings Migration

Use one additive migration with no opt-in backfill.

Extend `user_llm_settings` with:

- `generated_images_enabled BOOLEAN NOT NULL DEFAULT FALSE`
- `gemini_api_key_encrypted BYTEA NULL`
- `image_model TEXT NOT NULL DEFAULT 'gemini-3.1-flash-lite-image'`

Extend `bookmarks` with:

- `image_source TEXT NULL` with a database `CHECK` allowing only `scraped`, `screenshot`, or `generated`

`image_source` describes `image_url`, not `override_image_url`. It is internal provenance for acquisition and cost-control decisions and is never exposed by a template or presented as an AI label. Existing rows remain `NULL` (unknown); there is no unreliable provenance backfill. Every future write to `image_url` sets its corresponding source atomically with the URL. Clearing/replacing `image_url` also clears/replaces its source.

The Gemini key uses the existing AES-256-GCM `SecretBox` and `LLM_SETTINGS_ENCRYPTION_KEY`. The settings repository should accept a structured upsert value rather than adding more positional arguments. The key retains the established three-state behavior: blank keeps the existing ciphertext, an explicit delete checkbox clears it, and a nonblank value replaces it after encryption. Views expose only `has_gemini_api_key`; no server-to-client path returns decrypted key material.

The generated-image toggle is independent of the existing Anthropic/LLM `enabled` flag. Automatic and bulk generation require both the generated-image toggle and a decryptable Gemini key. The manual button is disabled when either prerequisite is absent. Model submissions must match the two-entry allow-list, while preserving an already-stored legacy value only long enough for the user to replace it, following the existing model-selector convention.

## UX

### Settings

Add one **Generated Images** section to the existing Settings page/form. It contains:

- **Generate a card image when none can be found** checkbox;
- write-only **Google AI Studio API key** control with saved/deleted states;
- **Image model** selector with Lite as default and Flash Image as the quality option; and
- a **Save settings** button associated with the existing form.

There is one form submission and the existing `POST /settings` → redirect behavior. The new section must not create a second form whose absent checkboxes could clear values in the first.

Update the existing Image Repair copy to state that a generated image may be used when fetch and screenshot acquisition find nothing. Its progress line distinguishes successful images from charged attempts, for example: `Generated: 7 — Attempts: 9 / 10`. When exhausted it reads `Generated: 7 — Attempts: 10 / 10 (cap reached)`.

### Cards and edit modal

Bookmark cards do not change. Immediately after create, an image-less bookmark shows the existing placeholder. A later page load or normal application refresh shows the generated image after the asynchronous write completes. There is no card polling and no AI label.

The edit modal adds one purple **Generate image** button beside the existing image controls. It issues an authenticated `POST /bookmarks/{id}/image/generate`, disables itself while the blocking HTMX request runs, and swaps the re-rendered card on success. A per-bookmark in-process guard returns `409 Conflict` for a concurrent duplicate click.

Manual generation writes `override_image_url` via the same atomic replace-and-cleanup path as upload. A later upload replaces it and retains precedence. **Restore original** removes the override and reveals the underlying `image_url`. Thus uploaded overrides always retain precedence, automatic generation never overwrites an override, and manual regeneration remains undoable.

## Background and Bulk Flow

### Create-time automatic flow

Bookmark creation performs metadata image acquisition and screenshot fallback as it does today. If both fail, the bookmark row is committed and returned without waiting for Gemini. Only then may an in-process asynchronous task be started.

The task receives an immutable generation context containing bookmark/user IDs and the bounded transient prompt data. Before calling Gemini it verifies:

- generated images are enabled for the user;
- a decryptable Gemini key exists;
- the bookmark still belongs to the user; and
- `effective_image_url()` is still empty.

It makes at most one provider call. On success it normalizes and stores the image, then conditionally updates `image_url` and `image_source = 'generated'` only if no effective image has appeared. This final compare-before-write protects a concurrent upload or manual image change. If the condition no longer holds, the newly stored object is deleted.

The task is intentionally best-effort and process-local. A server restart may abandon it; startup does not rediscover or retry it. Any provider, normalization, storage, or conditional-write failure is logged using safe structured categories and leaves the bookmark valid with its existing placeholder/image.

### Fix Missing Images bulk flow

The existing user-triggered repair job remains the explicit bulk/backfill mechanism. It continues to try metadata and screenshot acquisition first. It may then generate only for bookmarks with no effective image and eligible user settings.

The bulk limit is a hard, non-configurable **10 Gemini calls per run**. The cap counts attempts, whether successful or failed, so failures cannot bypass the spend bound. After 10 calls, remaining candidates are left untouched for a later user-triggered run. Existing per-user single-flight behavior remains. Progress events, settings JavaScript, and CLI output carry `generation_attempts`, successful `generated`, and `generation_cap: 10` consistently.

There are no automatic retries in either flow. Re-running the explicit bulk action or pressing **Generate image** again is a new user action, not a retry policy.

## Failure Semantics

Image failure never fails bookmark creation. Automatic failure leaves the placeholder and records no excerpt or raw provider detail. Manual generation returns a safe, actionable fixed message. Bulk generation increments `failed`, continues, and consumes one cap slot once the provider call begins.

Provider responses map to a small stable taxonomy:

| Category | Client-safe message |
|---|---|
| Missing/disabled user configuration | `Configure Generated Images in Settings first.` |
| Authentication/permission rejection | `The saved Gemini API key could not be used.` |
| Quota/rate limit | `Gemini image generation is currently unavailable for this key.` |
| Safety/policy refusal | `An image could not be generated for this bookmark.` |
| Timeout, transport, provider 5xx, malformed response | `Image generation is temporarily unavailable.` |
| Invalid or unsafe returned image | `The generated image could not be processed.` |

Messages are constants owned outside the adapter. Raw status bodies, prompts, page excerpts, decoded payloads, and credentials are never returned. Logs contain `user_id`, `bookmark_id`, selected allow-listed model, duration, trigger (`automatic`, `bulk`, or `manual`), and a fixed error category; they do not contain the key, prompt, excerpt, provider response body, or image bytes.

## Security and Privacy

- Gemini credentials are per-user, encrypted at rest, decrypted only for a call, and never rendered or logged.
- Bookmark title, description, tags, URL/domain, and a bounded transient page excerpt are sent to Google only after the user opts in. This third-party egress must be documented in product/release documentation even though no card label or excerpt helper text is added.
- Excerpts and prompts are transient and never persisted.
- Provider bytes are treated as hostile: bounded encoded size, header/dimension checks before full decode, maximum dimensions/pixels, decode validation, crop/resize, and JPEG re-encode strip provider metadata before storage.
- The processing semaphore is acquired after network completion, preventing a slow provider request from monopolizing image decoding.
- Automatic and bulk writes re-check ownership and effective-image state. Object keys remain unguessable and use existing tenant-safe cleanup for overrides.
- All costly browser endpoints are POSTs with existing authentication/CSRF posture; generation is never triggered by GET.
- `image_source` is internal and must not be added to card/settings view models solely for display.

## Test Strategy

### Unit tests

- Prompt construction: field delimiters, untrusted-instruction framing, missing fields, and deterministic truncation.
- HTML excerpt extraction: `article` → `main` → `body` ordering, script/style removal, whitespace collapse, meta-description fallback, Unicode-safe truncation, and no persistence representation.
- Model allow-list and Lite default.
- Settings behavior: default off, independence from Anthropic enablement, encrypt/replace/keep/clear, presence-only view, and decrypt failure.
- Gemini adapter against a local HTTP stub: request shape for both models, inline-byte success, auth/quota/safety/5xx/malformed response classifications, timeout, and proof that upstream bodies do not enter returned errors.
- Generation coordinator with fake service: automatic eligibility, one-call maximum, post-create return before fake completion, pre-call and pre-write override races, generated base write/source, orphan cleanup, and no retry after failure.
- Manual generation: writes override rather than base image, repeat generation cleans the previous owned override, upload still replaces it, and restore reveals the base.
- Normalization: non-image bytes, oversized encoded/decoded data, dimensions/pixel bounds, metadata stripping, and exact 1200×630 JPEG output.
- Bulk job: cap is exactly 10 calls, failures consume cap slots, candidates after the cap remain untouched, progress fields agree, and existing overrides cause a skip.

### Integration tests

With Postgres plus fake metadata, screenshot, storage, and image-generator adapters:

- migration defaults existing/no-row users to off and preserves existing bookmark behavior;
- each system image write atomically stores the correct `image_source`;
- asynchronous automatic success updates only the owning user's still-empty bookmark;
- concurrent override wins the conditional write;
- manual generation atomically replaces `override_image_url` without changing the base source;
- the bulk run persists at most 10 generated base images and emits a terminal event;
- settings ciphertext is not plaintext and no settings query/view returns the key.

### Browser tests

The committed Playwright harness uses a deterministic fake Gemini HTTP service and never reads a real Gemini key. Cover:

- Generated Images settings render, default off, save/reload, model choice, key presence-only state, and key deletion;
- forged model rejection and unauthenticated route rejection;
- create returns promptly with the normal placeholder, followed by a deterministic refresh showing the generated image;
- card markup has no AI label or pending UI;
- manual button disabled without eligible settings, success swaps the card, Generate again replaces the override, upload remains authoritative, and Restore original reveals the base;
- bulk progress stops at `Attempts: 10 / 10 (cap reached)` while reporting successful generation separately; and
- client-visible failures contain only the fixed messages.

### Isolated live-provider test

A live Gemini check is separate from normal tests and opt-in only. It exercises one generation with each allow-listed model against benign fixed prompt text, verifies decodable output, passes it through normalization, and deletes temporary output afterward. It must not create tracked files or fixtures.

The real key supplied for this task is an untracked runtime secret only. Testing must read it directly into the test process from its external secret file without printing it, shell tracing, copying it into the repository or `.env`, logging it, including it in fixtures, or capturing it in screenshots. Test output may report only model, pass/fail, duration, dimensions, and safe error category.

## Production Deployment and Smoke Testing

The captain authorizes deployment and monitoring after the ordinary merge/approval path. This authorization does not bypass review, CI, migration review, or the normal production release procedure.

After the approved merge:

1. deploy the application through the existing production path; startup applies the additive migration;
2. verify `/health`, migration completion, and normal bookmark creation before enabling the smoke account;
3. in the production web app, use a dedicated smoke user with its per-user Gemini key, enable Lite, create a known page with no metadata/screenshot image, confirm the create response remains prompt, then refresh until a generated base image appears;
4. verify the card has no AI label, the stored image is 1200×630 JPEG, and internal data records `image_source = 'generated'`;
5. use **Generate image** again, confirm `override_image_url` changes, then upload an image and confirm upload precedence and Restore original behavior;
6. run a bounded bulk smoke with more than 10 eligible fixtures and confirm exactly 10 provider calls are attempted and the production progress line reports the cap;
7. launch the iOS simulator configured against the production API, authenticate as the smoke user, create or fetch the smoke bookmark, refresh through the client's normal lifecycle, and verify the production-hosted generated image displays correctly; and
8. delete smoke bookmarks and generated/override objects, disable the smoke user's setting, and remove its saved Gemini key when the validation window ends.

No production smoke step prints or screenshots a key. Screenshots of product behavior, if required by the ordinary approval path, must contain no settings secret input and no sensitive bookmark content.

## Monitoring

For the initial production window, monitor production application logs, database errors, object-storage writes/deletes, and the smoke key's Google usage console. Safe structured events should distinguish generation started, succeeded, skipped, and failed, with trigger/model/duration and fixed category.

Watch specifically for:

- bookmark-create latency regressions (generation must remain post-response);
- authentication/quota/safety/timeout rates;
- normalization and storage failures;
- generated success count versus conditional-write skips;
- orphan cleanup failures;
- bulk runs exceeding 10 calls (any occurrence is a release blocker);
- repeated automatic attempts for one create (any occurrence is a defect); and
- elevated server memory/CPU during image normalization.

Because v1 adds no metrics backend, the first release uses structured logs plus provider/storage dashboards. A durable usage ledger or quota system is a separate future design.

## Rollback

If generation causes a production incident, roll back to the previously approved application release through the normal deployment mechanism. The additive nullable/defaulted columns remain in place; the previous binary ignores them, so a destructive down migration is neither required nor desired.

A restart/rollback abandons process-local automatic jobs and does not retry them. Existing generated `image_url` and overrides remain valid ordinary stored images. If data rollback is required for a specific bookmark, clear only a generated base URL/source or remove its override through ownership-checked application/admin tooling; do not bulk-delete unknown pre-existing images. Revoke the affected per-user Gemini key at Google when credential compromise is suspected, then clear its encrypted setting.

After rollback, verify health, ordinary metadata/screenshot acquisition, card rendering, uploads, and restore-original behavior. A corrected release must repeat fake-provider regression tests and the bounded production smoke before re-enablement.

## Separate Follow-up: Pre-existing Scraper Defects

The evidence reports reproduced two defects that predate generated images and are not included in this feature's approved scope:

1. `HtmlMetadataExtractor` does not reject non-2xx responses, so error-page title/description text can become bookmark metadata and prompt input.
2. `download_and_store_image` lacks a complete SSRF defense, download-size bound, and image-content validation; hostile remote bytes can be mirrored into public storage, including same-origin SVG risk.

These defects require a separate security/correctness follow-up with their own tests and review. The generated-image implementation must not silently fold unrelated scraper changes into its diff. Its provider-byte path is independently required to use strict normalization as specified above. The follow-ups remain open after this design is committed and should be prioritized independently; they do not change the approved generated-image behavior or authorize implementation work in this spec task.

## Resolved Decisions

There are no open product or architecture questions in this design. Google-only v1, per-user encrypted key, model choices, automatic asynchronous fallback, transient excerpt policy, quiet presentation, dual write paths, exact bulk cap of 10, no retries, fixed errors, fake normal tests, production smoke surfaces, and separate scraper follow-up status are all decided.
